## 기술 스택

| 기술 | 용도 |
|---|---|
| Python | 데이터 파이프라인 구현 |
| pandas | 데이터 정제 및 변환 |
| requests | API 데이터 수집 |
| Plotly | 인터랙티브 시계열 시각화 |
| JupyterLab | 데이터 탐색, 분석 및 시각화 검증 |
| pytest | 데이터 처리 및 계산 로직 테스트 |
| Ruff | 코드 검사 및 포맷팅 |
| GitHub Actions | 파이프라인 정기 실행 및 자동화 |
| GitHub Pages | 시각화 결과물 배포 |


## 상세 사용 이유
1. **pandas**: 스몰 데이터의 구조화된 데이터 처리 및 변환에 적합하며, CSV와 시계열 데이터를 쉽게 다룰 수 있기 때문
   - 대안: Polars, Modin 등
   - 선택 이유: 데이터 규모가 작아 분산 처리나 병렬 처리 기반의 추가적인 성능 최적화가 필요하지 않음
2. **requests**: 간단한 HTTP 요청으로 미국 재무부의 XML 데이터를 수집할 수 있고, 프로젝트의 요청 빈도와 데이터 규모에 적합하기 때문
   - 예상 요청 빈도: 기본적으로 하루 1회이며, 추가 검증을 수행하더라도 하루 10회 미만
   - 대안: httpx, urllib 등
   - `httpx`: 비동기 요청이나 HTTP/2 등 추가 기능이 현재 프로젝트의 요구사항에 필요하지 않음
   - `urllib`: Python 표준 라이브러리이지만, 간결한 HTTP 요청 구현과 응답 처리를 위해 requests를 선택
3. **Plotly**: Python 기반 데이터 처리 파이프라인과 연동하기 쉽고, 인터랙티브한 시계열 차트를 HTML로 생성해 배포할 수 있기 때문
   - 대안: Matplotlib, Tableau 등
   - `Matplotlib`: 정적 시각화에 강점이 있지만, 별도의 구현 없이 제공되는 인터랙티브 기능은 Plotly보다 제한적임
   - `Tableau`: 대화형 대시보드 구축에 적합하지만, 이번 프로젝트에서는 Python 코드 기반의 시각화 생성 및 HTML 배포가 더 간단함
4. **JupyterLab**: 데이터 탐색, XML 구조 확인, 초기 데이터 처리 로직 실험 및 시각화 결과 검증에 활용하기 위함
   - 최종 파이프라인 코드는 Python 모듈로 분리하고, JupyterLab은 탐색 및 실험 환경으로 사용
5. **pytest**: 데이터 처리 및 계산 로직을 자동으로 검증하기 위함
   - 대안: unittest 등
   - 선택 이유: 간결한 테스트 작성 문법과 다양한 플러그인 및 테스트 관련 도구를 활용할 수 있기 때문
6. **Ruff**: 코드 린팅과 포맷팅을 하나의 도구로 수행해 코드 품질과 일관성을 유지하기 위함
   - 대안: Flake8, Black 등
   - 선택 이유: 별도의 린터와 포매터를 조합하지 않고도 주요 코드 검사 및 포맷팅 작업을 통합할 수 있음
7. **GitHub Actions**: 별도 서버 없이 데이터 수집 및 처리 작업을 정기적으로 실행하고 자동화할 수 있기 때문
   - 대안: Apache Airflow 등
   - 선택 이유: 현재 파이프라인은 작업 단계와 의존성이 단순해 DAG 기반 워크플로 오케스트레이션을 위한 별도 환경을 운영할 필요가 없음
8. **GitHub Pages**: GitHub 저장소와 연동해 정적 시각화 결과물을 간편하게 배포할 수 있기 때문
   - 대안: 별도의 정적 웹 호스팅 서비스 등
   - 선택 이유: 서버 운영 없이 HTML 기반의 Plotly 시각화 결과를 공개할 수 있고, GitHub Actions를 통한 자동 배포와 연계하기 쉬움
